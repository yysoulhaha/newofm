# 设计说明

这份文档解释 newofm 为什么长这样：上游要求什么、代码里每个"奇怪"的处理对应哪条规则。

## 1. 请求流向

```
OpenAI 客户端
   │  POST /v1/chat/completions
   ▼
newofm :8920
   ├─ 目录解析（免费模型判定、上游地址、输出上限）
   ├─ 形状归一（会话 id、请求头、工具锚点、系统提示词）
   └─ 转发（恒 stream:true）
        ├─ 正常 → 直连上游，SSE 透传回客户端
        └─ 429 / 5xx 且配置了 NEWOFM_LANEB_URL → 转发到兜底端点
```

上游地址不是硬编码的：启动时拉取模型目录，读取其中 `api` 字段作为实际地址。
上游迁移端点时不需要改代码，`UPSTREAM_CHAT_URL` 只在目录抓取失败时兜底。

## 2. 上游准入的四个条件

四条里任意一条不满足都会被拒，而且**错误消息刻意与"额度耗尽"完全一致**，
这就是"明明还有额度却被 429"的根源。

| # | 条件 | 细节 |
|---|---|---|
| 1 | TLS 指纹 | 必须是 Bun 运行时。Bun 的 ClientHello 与官方 CLI 的 BoringSSL 一致，Node / Python / curl 会被直接拒绝。**这也是本项目用 Bun 写的唯一硬理由。** |
| 2 | 会话标识 | `user-agent: opencode/<channel>/<version>/cli`；`x-opencode-session` 与 `x-session-affinity` 同值，形如 `ses_<12hex><14chars>`，前 12 位 hex 必须是特定算法生成的形态（见第 3 节）。随机前缀会被拒。 |
| 3 | 工具锚点 | `tools` 数组里必须有名为 `read` 和 `shell` 的函数。**只校验名字**，不校验 description 与 schema，空 schema 的占位工具即可通过。 |
| 4 | 系统提示词 | 必须是官方 CLI 那份完整 harness 提示词原文。只发尾部 `<env>` 块、或换成通用助手提示，都会被拒。模板见 `harness_prompt.js`。 |

除此之外还有两条形状约束：请求体恒为 `stream:true`；不发送 `store` 字段。

## 3. 会话标识的算法

前 12 位 hex 是"位反转时间戳 + 同毫秒计数器"：

```
raw  = ~(timestamp_ms * 0x1000 + k) & (2^48 - 1)
id   = "ses_" + raw.toString(16) + 14 个随机字符
```

- `k` 从 1 起，同一毫秒内递增，**上限 63**；越界会进位到下一毫秒。
- 低 12 位恒为 `0xfff - k`，也就是说 **`k = 0` 对应的 `0xfff` 在真实会话空间里不存在**，
  出现即被识破。这是本项目最容易踩的一个坑：早期实现固定 `k=0`，
  换多少出口都是 429，且错误消息与额度耗尽一字不差。

同一会话内 `traceId` 保持不变、`spanId` 每请求新造；项目哈希口径是
`sha1("directory:" + cwd)`。

## 4. 工具面：core 与 full

`NEWOFM_TOOL_PROFILE` 控制发给上游的工具集：

| profile | 内容 | 适用 |
|---|---|---|
| `core`（默认） | `read` + `shell` 两个锚点，占位 schema | 请求体最小，够过准入 |
| `full` | 官方 CLI 真实发送的 12 个工具（edit / glob / grep / question / read / shell / skill / subagent / webfetch / websearch / write / execute，字母序） | 形状与官方完全一致，更不容易被按形状识别 |

两档的定义分别存在 `tools/gate_tools_core.json` 与 `tools/gate_tools_full.json`，
都是原样提取的，**不要手改**：函数级 `strict` 字段与完整 description 都属于准入形状的一部分。

注入占位工具时，系统提示词开头会加一句说明，劝模型不要去调它们；
如果模型仍然调用，客户端会收到一个它无法执行的 `tool_call`（见限制）。

## 5. 429 的两种含义

这是运维时最容易误判的地方。两类原因的处置完全相反，处置错了会互相伤害：
把还能用的出口或模型一起判死。

| 证据 | 判定 | 正确处置 |
|---|---|---|
| `retry-after` 很长（几小时量级） | 该 **出口对应该模型** 的额度桶已空 | 只冷却 `(出口 IP, 模型)` 这一组合，同一 IP 上的其它模型照常可用 |
| `retry-after` 很短或缺失 | 短时冷却 / 原因未知 | 出口级冷却，换节点 |
| 请求形状不全（缺 `shell`、系统提示过短、计数器越界） | 伪装的 429，与额度无关 | 修形状，换 IP 无效 |

冷却表持久化在缓存目录下，重启保留、过期自动清理，可通过 `/health` 观察。
轮换时会把处于冷却的 `(IP, 模型)` 排到候选末尾，避免在同一个模型上反复撞墙；
切换成功后该组合的冷却立即清除。

## 6. 出口与额度

上游额度按 **出口 IP** 划分，滚动窗口内计数。因此：

- 换节点 ≠ 换出口：多个节点可能共用同一个 egress IP，必须做 IP 去重，否则会在死池之间打转。
- 换出口后要确认真的换了：代理的 PUT 只代表"选择已记录"，已在建立的连接仍可能走旧节点。
  所以切换后需要等一小段时间，再用一次 trace 请求校验真实出口 IP。
- 候选全败要回滚到原节点，不能把组停在最后试过的死池上。

如果本机有 mihomo / Clash 的控制口（unix socket），可以开启自动轮换：

```bash
NEWOFM_CLASH_SOCK=/path/to/mihomo.sock NEWOFM_CLASH_GROUP=你的代理组名 \
  bun newofm.js
```

两者都没有配置时，轮换功能自动关闭，不影响正常转发。

## 7. 流式与超时

上游恒定流式，非流式客户端由网关聚合 SSE 后再返回。

超时必须分层，否则长回答会被误杀：

- `UPSTREAM_HEADERS_TIMEOUT_MS`：只覆盖"等待响应头"这一段。
- `UPSTREAM_IDLE_TIMEOUT_MS`：覆盖读流阶段的空闲时间，只要还在出数据就一直续期。
- 客户端主动断开时，取消信号会透传到上游，避免空转消耗额度。

流结束时会补齐 `finish_reason` 与 `[DONE]`；如果上游中途断流，
已收到的内容会正常收尾，而不是抛给客户端一个错误。

## 8. 测试

`bun test tests/newofm.test.js` 共 57 个用例，全部离线：

- A 段：纯函数与形状构造的确定性断言（会话 id、请求头、工具注入、提示词渲染）。
- B 段：mock fetch 的集成测试（重试、轮换、冷却、流式收尾、取消传播）。
- D 段：历史回归项，防止优化时再次踩回同一个坑。

测试通过 `NEWOFM_CACHE_DIR` 指向临时目录，不会写到真实缓存，也不会触碰真实出口。

## 9. 边界与限制

- 上游的准入规则可能随时变化。本项目是对**可观测行为**的工程实现，不保证长期有效；
  规则变化时通常表现为"突然大面积 429"，需要重新做形状对照。
- 静态模型表是启动兜底，实际可用模型以实时目录为准；目录里标记为付费或已废弃的会被过滤。
- 除可选的兜底转发外，没有内置的多上游调度。需要自己提供备用端点。
- 注入的占位工具会让模型"以为"自己有工具可用。对纯对话场景无影响，
  对需要真正执行工具的 Agent 客户端，应关闭工具注入或改用自己的工具。
